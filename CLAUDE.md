# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

`headroom` answers two questions and acts on the answers: **which of this machine's Claude Code and Codex accounts has quota left** (`headroom accounts`, the board: live limit bars, a page per vendor switched by tab, refreshing while it is open, enter records the chosen account for that vendor) and **which session do I get back into, on which account** (`headroom sessions`: every session on the machine in one picker, Claude Code only — transcripts are machine-global — entered in its own project dir and continued, by exec, on the account that last drove it; the retired `resume` spelling is a permanent tombstone). Account launches go through `headroom launch`, which owns launch routing: it validates the account and execs `claude` (or `codex`, under `--vendor codex`) with an environment built from that decision alone. `headroom check` verifies the reverse-engineered vendor facts all of it rests on. The mental model and those vendor contracts live in [DESIGN.md](DESIGN.md) — read it before touching the parsers, `check`, the session store, or anything Keychain-related; § A second vendor: Codex before touching anything vendor-scoped.

`README.md` is the user-facing story (use cases, install, setup); `docs/REFERENCE.md` holds the command table, how-it-works, shell integration and configuration — a change to a command or flag lands in both the reference and the skills. `skills/` ships two agent skills (`headroom`, `headroom-setup`) installable with `npx skills add qiushiyan/headroom`; they describe use patterns in terms of engine commands only — a change to a command's name, flags, or output wording is a change to them.

## Commands

```bash
make build            # go build ./...
make install          # build → ~/.local/bin/headroom
make test             # go test -race ./...
make vet / make fmt
make check            # vet + test
make test-pty         # expect(1) harness for the interactive surface

go test ./internal/usage -run TestDriftTags   # single test
```

Raw-mode terminal behavior (picker interaction, self-refresh, signal-time
restoration) is out of `go test`'s reach — `make test-pty` drives it through
a real pty; see DESIGN.md § Verification and `test/pty/run.sh`.

## Architecture

The vendor set is closed at `claude` and `codex`. `config.Load` resolves one `Scope` per vendor — paths, binary, usage URL, request spacing, launcher format, environment policy, presence — and refuses accounts roots that alias each other. `accounts.Discover(scope)` returns a `Set` that owns `Select`, `SetCurrent` and `KnownExtraDir`; an `Account` carries its scope, so no operation takes a scope beside an account. The set travels with whatever was built from it — the prepared list, the board page, the disk snapshot — and is never rebuilt from a scope plus a list. Each vendor keeps its own `.current`, `.order` and `state.json` under its own accounts root.

Account facts and live requests have separate owners:

- `accountstate` assembles discovery, strict `.current` resolution, the newest usable disk observation and a Codex account's plan. It owns `Health`, `Observation` and `Attempt`, independent facts consumed by rendering and JSON. Its read operation has no credential, health-probe or HTTP dependencies. `limits` reads here and stops.
- `refresh` owns credential/identity eligibility, durable request claims, parallel fetches, response interpretation and completion recording. A candidate binds its ledger key, vendor, prepared request and expected response identity behind unexported fields; `Start` takes the scoped store and refuses a candidate of the other vendor. The board and `check` share it; each retains its own health policy and interpretation of the result for its audience. Received observations and persistence errors travel separately.
- `state` owns the cross-process request ledger, stored response bodies and explicit session re-homes, one store per accounts root, opened from a scope. Claims authorize traffic; generations protect against late completions; every deadline takes the scope's spacing as a floor. Its bounded legacy import is described in DESIGN.md § The one file headroom writes.
- `render` draws the block and compact account layouts and pure session rows. JSON serialization stays with the command surface; schema 5 exposes the same facts and drift tags, with a vendor on every account and `current` keyed by vendor.

`app/accounts.go` owns selection, scheduling and the board's keymap. The board is one page per present vendor; a page owns its list, selection, schedule and its refresh round — one list and channel until the channel closes and drains — so a result lands on the page that started it, and only the visible page starts rounds. `picker.step` is one turn of the loop and the only place results are routed and rounds started; only that receiving path updates facts. Selection survives rediscovery by account name. Off a terminal the board prints one frame; `--json` serializes the same result.

`internal/sessions` collects transcripts, history and registry evidence. One PID sample per collection supplies both liveness and ownership; mutations re-inspect at action time. `app/resume.go` owns the session picker's interaction state, while `app/session_actions.go` owns routing, resume and mutation effects. The collector and state store share the session domain's re-home record.

`launch.Prepare` validates routing, topology and executable resolution and builds the environment before either launch surface persists a choice. Callers own `.current` or re-home writes and process replacement. A failed exec leaves a successfully recorded choice intact and reports that fact. `internal/tui` owns raw-mode lifetime, signal restoration and physical-key decoding; surfaces own keymaps and frame policy.

Load-bearing choices:

- **Vendor variation enters as scope data and three document readers, nothing else.** Paths, names, spacing and the environment policy are data on the scope. Vendor documents are read at three dispatch points — identity at discovery (`accounts`), access at preparation (`app`: health plus a candidate or the attempt state that blocks one), and the usage body (`usage.Parse(vendor, body)`, shared by live interpretation, replay and `check`). What a vendor supports as a command (the Codex removal refusal, Claude Code-only sessions, each vendor's checks) is decided in the command that owns it, never pushed into a scope flag. A second spelling of claims, launch rules or freshness is the drift this exists to prevent.
- **Identity travels with every observation.** A Codex account carries the one `auth.json` snapshot discovery took (`codexauth`); labels, the ledger key (`uuid:<account_id>/<user_id>`, both required, permanent) and the request's credentials all come from it for the whole round; the one later read — `check` sampling the token after a 401 — is diagnostic and can replace none of them. A usage body naming another account or user is recorded as unparseable and never shown, live or replayed (`usage.Reading.BelongsTo`). An account that cannot say whose it is has no ledger key: no claim, no replay. Usage is never derived from Codex rollouts — they carry no account identity and the shared store mixes accounts in one file.
- **An account has three independent axes, never one status.** `Health` (can Claude Code use it — only `/login` fixes a bad answer), `Observation` (rows, always carrying `ObservedAt` and `Source`, plus the account-level allowance: only positive, well-typed vendor evidence blocks, `Actionable` consults it, and unknown — every Claude Code response — is never read as allowed), `Attempt` (how the newest request went — never a statement about the account). Collapsing them is the bug this model exists to prevent: a 429 or an aged-out access token must annotate what is known, never erase it or read as account failure. Rows never travel without their timestamp.
- **The two credential expiries mean different things.** `expiresAt` (~8h) aging out is routine — Claude Code refreshes it silently, and the correct response is "any `x-…` session refreshes it", never "/login". Only `refreshTokenExpiresAt` (~30d) passing means a human must act, and only on positive evidence: an absent or unparseable field is never read as expired.
- **One parser per vendor document type; no duplicate parse paths.** `creds.Parse`, `usage.ParseLimits` (live *and* Claude Code's cached copy — identical shape), `auth.Parse`, `codexauth.Parse` (Codex's `auth.json` and the JWT payloads in it), the Codex usage parser behind `usage.Parse`, and the session readers `sessions.ParseTail`, `sessions.ParseHistory` and `sessions.ReadRegistry` are the only readers of vendor data. Attribution and title checks compare *decoded fields*, never substrings — transcript and prompt bodies quote UUIDs and record-type strings verbatim, and a substring match has already caused both a mis-attribution and a false `check` FAIL. Renderer and checker share them: rendering tolerates malformed fields without dropping the account, and degrades *visibly* — a bad percent renders as a `?` bar with a drift marker, never as a `0%` that reads like free headroom. Every degraded field carries a `tag.State`; `--json` exposes the tags, and `check` fails on any `bad`. Limit rows carry the vendor's decoded identity (`kind`/`group`/`model`, and for Codex `feature`/`window_seconds`) beside the label derived from it; the three field states never widen — an unstarted Codex window is a flag on the row — machine consumers select rows by those fields, never by matching label prose.
- **The usage endpoint's budget is per account** (~1/min for Claude Code; Codex's is unmeasured and starts at the same spacing as a local policy), and headroom's own surfaces are its main consumer. `state.Claim` is the single authorization: it decides eligibility and records the claim inside one lock, so the permit it returns — never a flag computed earlier — is what lets a request leave. Deciding eligibility anywhere else reopens the window where two processes both fetch. Backoff means no traffic; a refused request may itself count against the budget. Never add a retry inside a run.
- **headroom stores what it bought, not just what it spent.** A run inside its quiet period replays its own newest response rather than falling back to Claude Code's cache, which is written only when Claude Code itself fetches and is routinely a day old. Bodies are stored raw so the vendor's usage parser, reached through `usage.Parse`, stays their only reader. See DESIGN.md § The one file headroom writes for the corruption policy — the ledger is disposable and self-heals quiet, re-homes are human decisions and are never written over.
- **Read-only against the vendors, with three documented exceptions, all Claude Code's**: no Codex file is ever written, and the usage client only ever issues a GET (the same Codex backend has a POST that spends a reset credit). the Keychain is never written by an observation path, token refresh belongs to Claude Code, login and quota state are never touched. headroom writes two files of its own, atomically: `state.json` (its request ledger, the responses it fetched, and explicit session re-homes only — ordinary resumes write nothing; the launch itself becomes vendor evidence) and `.current` (one routing fact, headroom's alone to read and write — per vendor; the discovered set's strict `Select` is its only reader, and corruption refuses rather than defaulting; see DESIGN.md § The launch surface). The exceptions are the resume picker's `r` (appends one vendor-format `custom-title` record), `dd` (deletes a transcript), and `accounts remove` (deletes the removed account's own Keychain item — `creds.DeleteKeychainItem`, its only caller); all three are explicit user commands naming their object and all are refused while a session is live or liveness is unverifiable. The account set changes only through `accounts add` / `accounts remove` (`accounts/lifecycle.go` + `app/lifecycle.go`): seeding builds exactly what `VerifyTopology` accepts and verifies itself against it; see DESIGN.md § The account lifecycle. Codex accounts are added the same way and never removed: headroom has no evidence of whether a Codex session is running on a home, and an empty liveness read is not inactivity.
- **A session's owner is evidence, newest-wins, never re-stamped.** Verified live registry > newest of {explicit re-home, newest history prompt}; degraded attribution (no evidence, deleted account, same-instant conflict) falls back to the current account *visibly*. Resume never writes `.current` — that file means "where new sessions go" and only `headroom accounts` moves it.
- **A launched child's environment is a total function of the validated account decision** — the vendor's row of one policy table (`config.EnvPolicy`), applied by one constructor, touching only that vendor's variables: every inherited `CLAUDE_CONFIG_DIR` stripped, exactly one set for a non-primary, the primary selected by absence; for Codex `CODEX_HOME` likewise, with `CODEX_SQLITE_HOME`, `CODEX_API_KEY` and `CODEX_ACCESS_TOKEN` stripped because they outrank the home, and a credential's value never printed. `launch.Target` is the seam and its constructors the only door; no surface may mint a primary decision from corrupt routing state (resume's owner→current fallback refuses past current, never falls to primary). A neutralized ambient value stays visible *when unexplainable* (relative, unknown, or the primary dir spelled explicitly): launch stderr, board note, `check` detail — through the target's conflict classifier plus the discovered set's `KnownExtraDir`, which quiets the one ordinary case (a value naming a discovered extra's dir means "this shell lives inside a managed session"; `check` still reports it). Dirs crossing the seam are absolute, enforced at construction and at `config.Load` — a relative `CLAUDE_CONFIG_DIR` makes claude run as the *primary* while writing state beside the cwd (verified 2.1.220; see DESIGN.md § The system observed). Launch also verifies the shared-sessions topology (`accounts.VerifyTopology`, shared with `check`) and refuses a primary launch under a re-pointed `HEADROOM_HOME` — both before any `.current` write.
- **Accounts fail independently**: any per-account problem becomes that account's rendered status line, never a process failure.
- **`check` distinguishes "broken" from "couldn't test"**: PASS / FAIL / INCONCLUSIVE (exit 0/1/2). Rate limiting, transport failure and a stale access token are inconclusive, not drift — and so is any Codex 401, because Codex recovers from one by refreshing. It runs every present vendor's group and its closing line blames the vendor whose assertion failed. It also separates its own files from the vendor's: a corrupt `state.json` must never report as "Claude Code changed a format".
- **stdlib + `golang.org/x/term` only** — no CLI/TUI frameworks, no cgo. Parsing is pure functions tested by table; exec and HTTP stay at concrete operation boundaries (`internal/app` wires them).
